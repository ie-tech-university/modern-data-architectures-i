1.1 Structured data

Information with a high degree of organisation, in two dimensions: rows and columns.

Every record of the same table has exactly the same attributes, in the same order.

Examples: relational database tables, CSV files, spreadsheets.

TABLE customers
customer_idfirst_namelast_nameemailcreate_date
1JohnDoejd@gmail.com2004-05-07
2JaneDoejd2@gmail.com2002-09-24
3JohnSmithjs@gmail.com2010-03-12
4JaneSmithjs2@gmail.com2008-12-31

CSV: comma-separated values

customer_id,first_name,last_name,email,create_date
1,John,Doe,jd@gmail.com,2004-05-07
2,Jane,Doe,jd2@gmail.com,2002-09-24
3,John,Smith,js@gmail.com,2010-03-12
4,Jane,Smith,js2@gmail.com,2008-12-31

Simple, universal and human-readable: every tool can open a CSV. But…

Why CSVs are tricky

No data types

Is 00123 a number or a postcode? Is 2004-05-07 a date? You must decide for every column.

The header is optional

Is the first line data or column names? The file doesn't say.

The delimiter varies

In Spain, Excel often uses ; because the comma is the decimal separator: 3,14;Madrid.

Commas inside values

Real TfL data: BikePoints_1,"River Street , Clerkenwell",51.529163 needs quotes to keep the name in one column.

import pandas as pd
df = pd.read_csv("customers.csv", sep=";", decimal=",",      # Spanish-style CSV
                 dtype={"postcode": str}, parse_dates=["create_date"])

1.2 Semi-structured data

Information with a self-describing structure: each value travels with its name.

  • Often more than two dimensions: nested elements and collections
  • Records of the same kind may have different attributes, in a different order

Examples: JSON, XML, YAML.

[
  { "customer_id": 1, "first_name": "John",
    "last_name": "Doe", "email": "jd@gmail.com",
    "create_date": "2004-05-07T00:00:00.000Z" },
  { "customer_id": 2, "first_name": "Jane",
    "last_name": "Doe", "email": "jd2@gmail.com",
    "create_date": "2002-09-24T00:00:00.000Z" }
]

JSON's flexibility, in four rules

1 · Field order doesn't matter 
{"customer_id": 1, "first_name": "John"}
{"first_name": "John", "customer_id": 1}
Both are the same record
2 · Records may have different fields 
{"customer_id": 1, "first_name": "John"}
{"customer_id": 2, "first_name": "Jane",
 "gender": "female"}
Both are valid
3 · Collections with [ ] 
{"customer_id": 1,
 "emails": ["jd@gmail.com",
            "john.doe@hotmail.com"]}
Many values in one field
4 · Nested objects with { } 
{"customer_id": 1,
 "address": {"street": "María de Molina",
   "number": 11,
   "coordinates": {"lat": 40.437, "lon": -3.686}}}
As many levels as you need

Real-world JSON: a TfL bike point

{
  "id": "BikePoints_1",
  "commonName": "River Street , Clerkenwell",
  "additionalProperties": [               ← collection
    { "key": "NbBikes", "value": "7",      ← nested objects
      "modified": "2026-10-15T21:09:12Z" },
    { "key": "NbEmptyDocks", "value": "11", … }
  ],
  "children": [],                            ← empty collection
  "lat": 51.529163,                          ← numbers
  "lon": -0.10997
}

The data you ingested in the TfL lab uses every JSON feature: strings, numbers, collections and nested objects.

Notice: "value": "7" is a string, not a number. JSON keeps types, but only the ones the producer chose.

JSON Lines: JSON for big data

JSON array · one big document

[
  {"id": "BikePoints_1", "NbBikes": 7},
  {"id": "BikePoints_2", "NbBikes": 2},
  …
]

You must read the whole file before you can parse it.

JSON Lines · one record per line

{"id": "BikePoints_1", "NbBikes": 7}
{"id": "BikePoints_2", "NbBikes": 2}
…

Each line is a complete JSON object: easy to split, stream and append. Extensions: .jsonl, .ndjson.

Spark, Kafka consumers and most log tools prefer JSON Lines: spark.read.json() expects one object per line by default.

XML: extensible markup language

<?xml version="1.0"?>
<customers>
  <customer>
    <customer_id>1</customer_id>
    <first_name>John</first_name>
    <last_name>Doe</last_name>
    <email>jd@gmail.com</email>
  </customer>
  <customer>
    <customer_id>2</customer_id>
    <first_name>Jane</first_name>
    …
  </customer>
</customers>

Data wrapped in opening and closing tags, nested as deep as needed.

  • More verbose than JSON (every name appears twice)
  • Still common in banking, government, office documents and enterprise integrations
  • New APIs mostly use JSON

How contents are encoded

Text files vs binary files

Text files

  • Can only store text: letters, numbers, punctuation
  • Open and edit them with any text editor

customer_id,first_name,last_name
1,John,Doe
2,Jane,Doe

Binary files

  • Can store any type of data as raw bytes, mostly not human-readable
  • Meant to be opened with a specific application

Text files depend on encodings

An encoding maps characters to bytes. The same letter can be stored differently:

é→c3 a9UTF-8
é→e9Latin-1 (ISO-8859-1)

Read UTF-8 bytes as Latin-1 and "José" becomes "JosÃ©": the famous mojibake.

Rule of thumb: write and read UTF-8. It covers every language and is the default for JSON, the web and Python 3.
open("clientes.csv", encoding="utf-8")
pd.read_csv("old_export.csv", encoding="latin-1")

Big data storage formats

Binary formats built for analytics

Two kinds of binary files

Data formats

Store one kind of content for a specific app: images, audio, PDF, office documents.

Storage formats

Store tables efficiently to improve the storage and performance of big data applications: Parquet, ORC, Avro.

Row vs columnar layout

Row-oriented · CSV, Avro
1John72Jane23Ana9
Great to write and read whole records
Columnar · Parquet, ORC
123JohnJaneAna729
Great for analytics: read only the columns you need, compress similar values

Parquet, ORC and Avro

Apache Parquetcolumnar

The default analytics format: Spark, pandas, DuckDB, BigQuery, Snowflake, Databricks all speak it.

Basis of lakehouse tables (Iceberg, Delta)
Apache ORCcolumnar

Optimized Row Columnar, born in the Hive/Hadoop world. Similar ideas to Parquet.

Mostly in Hive-based platforms
Apache Avrorow

Compact rows with an embedded schema that can evolve. Ideal for messages and streaming.

Very common with Kafka
All three are self-describing: the schema (column names and types) travels inside the file. No more guessing like with CSV.

799 stations × a snapshot every 5 minutes × 24 h = 230,112 rows, 10 columns, saved in five formats:

Parquet is about 24× smaller than CSV and 50× smaller than JSON: station names and coordinates repeat every 5 minutes, and columnar compression loves repetition.

Reading just 2 columns from Parquet took 0.01 s, versus 0.24 s to load the whole CSV, on the same laptop.

Simulated from one real BikePoint response (October 2026) with small random changes per snapshot.

Try it yourself: CSV to Parquet

import pandas as pd

df = pd.read_csv("day.csv", parse_dates=["ts"])
df.to_parquet("day.parquet")                       # needs pyarrow

# read only the columns you need: Parquet skips the rest of the file
bikes = pd.read_parquet("day.parquet", columns=["name", "NbBikes"])

# the schema travels inside the file
import pyarrow.parquet as pq
print(pq.read_schema("day.parquet"))
# ts: timestamp[ns]   id: string   name: string   lat: double   NbBikes: int64 …
In Spark it's the same idea: spark.read.csv(...).write.parquet("s3a://datalake/curated/tfl/")

Summary

What to remember

Summary

  • Data has different degrees of organisation: structured, semi-structured and unstructured.
  • Big data solutions store data in files (text or binary) in distributed file systems and object storage.
  • Text files depend on encodings: the encoding defines which characters the file can contain. Use UTF-8.
  • Binary files come in two types: data formats (images, audio, PDF…) and storage formats (Parquet, ORC, Avro) that improve storage and performance.
  • Rule of thumb for the data lake: land raw data as it arrives (often JSON/CSV), then store curated data as Parquet.
