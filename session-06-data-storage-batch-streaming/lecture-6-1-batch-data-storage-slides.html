Today we zoom into batch storage: the technologies, their limits, and how to organise a data lake on top of them.

1.1 Two storage families

Distributed file systems

Data stored as files in a hierarchical folder structure.

Object / blob stores

In object stores, folders don't exist

What is really stored

Object stores have a flat namespace. Tools pretend there are folders by splitting keys on /:

# "list the folder" = list keys with a prefix
s3.list_objects_v2(Bucket="bucket1",
                   Prefix="folder1/", Delimiter="/")
Consequence: "renaming a folder" in S3 means copying and deleting every object under that prefix. In HDFS it's a single, instant metadata change.

File system or object store?

In terms of functionality, there's no difference for a data lake: both store any file, at any scale.

Where they differ

  • Permissions: file systems set access once per folder; object stores use policies per object or per key prefix
  • Renames and moves: instant in a file system, copy + delete in an object store
  • Cost and operations: cloud object stores are cheap, always on and fully managed
In practice (2026): most new data lakes run on cloud object storage. Governance tools such as Unity Catalog or AWS Lake Formation add folder-like permissions on top.

1.2 What batch storage is NOT good at

⏱ Low-latency access

Answering in tens of milliseconds

Solution: a serving layer
🗂 Lots of small files

Millions of tiny files slow everything down

Solution: compaction
✎ Random modifications

Editing a file in the middle

Solution: rewrite files (or a table format)

Challenge 1: low-latency access

1 ms10 ms100 ms1 s10 s
Serving layer NoSQL, key-value
Batch storage S3, HDFS, ADLS

Batch storage is optimised for high throughput (reading terabytes) at the expense of latency (time to the first byte). Apps that need answers in tens of milliseconds can't query it directly.

Solution: copy the results an app needs into a serving layer, typically a NoSQL datastore. Example: the bike app reads "bikes available now" from a key-value store, not from the lake.

Challenge 2: lots of small files

Before · 288 files × 7 KB
one file per 5-minute snapshot
compact →
After · 1 file
one Parquet file per day

Every file costs a list call, a metadata entry, an open/read request and often a processing task. Thousands of tiny files = thousands of overheads.

Aim for files of hundreds of MB (typically 128 MB–1 GB). Data engineers spend real time compacting small files.

# Spark: read many small files, write a few big ones
spark.read.json("s3a://datalake/raw/tfl/bikepoint/2026/10/15/") \
     .coalesce(1).write.parquet("s3a://datalake/std/mobility/bikepoint_status/dt=2026-10-15/")
# Delta Lake does it for you:  OPTIMIZE bikepoint_status

Challenge 3: no random modifications

On your laptop
✎ edit line 2
In batch storage
✗ edit in place✓ append at the end
or rewrite the whole file

You can't edit a file like on a regular computer. The only operations are append (HDFS) or rewrite the whole file (object stores).

2026 solution: table formats. Delta Lake and Apache Iceberg let you run UPDATE, DELETE and MERGE: they rewrite only the affected files and record the change in a transaction log.
MERGE INTO std.bikepoint t
USING updates u ON t.id = u.id
WHEN MATCHED THEN UPDATE SET t.bikes = u.bikes
WHEN NOT MATCHED THEN INSERT *

What is a data lake?

A centralised repository that lets companies store all their data at any scale.

  • Data is stored as-is, without structuring it first
  • The goal: make all company data available for analysis
  • The main reason the batch storage layer exists

Stages from Alex Gorelik, The Enterprise Big Data Lake.

Puddle, pond, lake, ocean

Data puddle

A single-project data mart built with big data tech. Well-known data; big data is used to lower costs or go faster. Usually the first step.

Data pond

A collection of puddles. Data limited to what projects need. High IT cost, little data democratisation or self-service.

Data lake

Two key differences: self-service (users find and use data without IT) and data relevance (data kept even if no project needs it yet).

Data ocean

Extends self-service and data-driven decisions to all the data in the company.

Data swamp: a failed data lake, with no governance, irrelevant data and poor quality. Nobody trusts it, so nobody uses it.

2.2 Two prerequisites for success

🐷 The right data

The lake is like a piggy bank: you often don't know what you're saving for, but you want it when you need it.

Since you don't know how data will be used, don't transform it prematurely: keep as much as possible in its native (raw) format.

🍽 The right interfaces

Everyone should use the lake, but they want different things:

Data scientists"raw ingredients, please"
Analysts"a cooked, prepared meal"

So the lake has multiple zones, and users must be able to find the right data (a catalog).

  • Original format and structure: structured, semi-structured or unstructured
  • Unclean: not for direct consumption
  • Immutable: never edited; changes arrive as new copies
  • Kept forever (old data can move to cheaper storage tiers)
  • Only data engineers and technical developers get access
Why keep raw data? To replay (rebuild silver and gold after a bug) and to repurpose (answer new questions nobody planned for).

Standardized zone (silver)

  • Data from raw, standardized in a big data format (Parquet, Delta, Iceberg) to make applications faster
  • Curated: cleaned, sanitised, standardised and deduplicated, which builds trust (veracity)
  • Organised by business area and partitioned by how it's consumed
  • Clean and secure, so it can be published for ad-hoc queries, usually through SQL external tables and views
# raw JSON → silver Parquet, partitioned by day
from pyspark.sql import functions as F
raw = spark.read.json("/raw/tfl/bikepoint/2026/10/15/")
(raw.selectExpr("id", "commonName AS name", "lat", "lon")
    .dropDuplicates(["id"])
    .withColumn("dt", F.lit("2026-10-15"))
    .write.mode("overwrite")
    .partitionBy("dt")
    .parquet("/std/mobility/bikepoint_status/"))

-- then expose it with SQL
CREATE EXTERNAL TABLE std.bikepoint_status …
LOCATION '/std/mobility/bikepoint_status/';

Curated zone (gold)

  • Cleansed, enriched and modeled versions of silver data, similar to the ETL that builds a data warehouse (conformed dimensions, master data)
  • Unlike a warehouse, there may be several versions of the same data for different projects, so it's organised by project or domain
  • Usually managed by IT, exposed with SQL tables and views, and documented in a data catalog
-- gold: average bikes available per station and day
CREATE TABLE gold.daily_availability_by_station AS
SELECT dt, id, name,
       AVG(bikes) AS avg_bikes,
       MIN(bikes) AS min_bikes
FROM   std.bikepoint_status
GROUP  BY dt, id, name;

Other examples: /gold/edw/dim_customer, /gold/edw/daily_sales_by_customer.

Work zone and sensitive zone

🧪 Work (sandbox, development)

  • Where most analysis and experimentation happens
  • Organised by user, project or subject: /work/users/ana, /work/projects/customer_churn
  • A private space per user, plus shared project spaces
  • When work becomes a product, it's promoted to gold

🔒 Sensitive

  • Data to protect for regulatory (GDPR) or business reasons
  • Only data stewards and authorised people or apps get access (e.g. HR sees employee data)
  • Keep an encrypted copy here and a redacted copy in gold
  • Grant access explicitly and temporarily; de-identify (anonymise or pseudonymise) for analytics

Modern catalogs can also mask columns or filter rows per user, so not every protection needs a separate copy.

From data lake to lakehouse

What table formats add

Data lake + table format = lakehouse

Engines: Spark · SQL · BI · ML
Catalog: tables, permissions, lineage
Table format: Delta Lake · Apache Icebergtransaction log, ACID, time travel
Object storage: Parquet files in raw / std / gold

A lakehouse keeps the cheap, open files of the data lake and adds what warehouses had:

  • ACID transactions: no half-written tables
  • UPDATE / DELETE / MERGE: solves challenge 3
  • Automatic compaction: helps with challenge 2
  • Time travel: query yesterday's version of a table

The zones stay the same: bronze, silver and gold just become tables.

Summary

What to remember

Summary

  • Batch storage is file-based, in two families: distributed file systems and object / blob stores.
  • Data engineers handle its challenges by compacting small files, rewriting files when data changes (or using a table format) and copying data to a serving layer for low latency.
  • Batch storage hosts the data lake, which grows in stages: puddle → pond → lake → ocean.
  • Data lakes are organised in zones: landing, raw (bronze), standardized (silver), curated (gold), work and sensitive.
