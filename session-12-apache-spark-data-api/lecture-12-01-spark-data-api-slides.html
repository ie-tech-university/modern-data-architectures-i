Spark APIs

How your Python code talks to Spark

What is an API?

Application Programming Interface: a software interface that lets two applications or technologies talk to each other. In practice, one of two things:

📦 A library or module

You import it in your programming language and call its functions. This is how we use Spark.

from pyspark.sql import SparkSession
spark = SparkSession.builder.getOrCreate()
spark.range(10).count()      # 10
⇄or
🌐 A remote service (REST API)

You send HTTP requests and get data back, usually JSON. Spark has one too: the monitoring API behind the Spark UI.

Building blocks: low-level vs high-level

Spark APIs give us data structures and functionality to process data independently of its location and format. They come in two layers:

  • High-level (Structured) APIs: DataFrames, Datasets, SQL. What you'll use 95% of the time.
  • Low-level APIs: RDDs and distributed shared variables.

Spark and functional programming

Spark is written in Scala, a functional language on the JVM where functions are first-class citizens: you can pass them around like any value.

Spark uses this paradigm to run transformations on datasets held in the cluster's memory. Python is multi-paradigm, so PySpark can use the same style.

ScalaJVM·Python+Spark=PySpark 
# 1. functions are values: pass one to Spark
def is_good(rating):
    return rating >= 4.0

ratings_rdd.filter(is_good)

# 2. ...or an anonymous function (lambda)
ratings_rdd.map(lambda r: r * 2)

# 3. data is never modified: each step
#    returns a NEW dataset
good = ratings_df.filter(F.col("rating") >= 4)

Spark ships your function to the executors and runs it on every record, in parallel.

Core concepts

Partitions, transformations and actions

Three ideas you need for every Spark API

🧩Partitions

Data is split into chunks spread across the cluster. Each executor works on one partition at a time: that's where parallelism comes from.

📝Transformations lazy

Describe what to do (filter, select, groupBy…). Spark only records them in a plan.

▶️Actions eager

Run the plan and return or save a result (count, show, write…).

The same three ideas apply to RDDs, DataFrames and SQL. Learn them once, use them everywhere. Examples in this lecture use the MovieLens files you ingested into HDFS in lab 8.1: 100,836 ratings and 9,742 movies.

2.1 Partitions

Partition: a chunk of data physically distributed across the cluster (with DataFrames, a subset of the rows). Parallelism: the balance between # partitions and # cores.

Partitions in practice

ratings = spark.read.csv(
    "hdfs://localhost:9000/datalake/raw/movielens/ratings",
    header=True, inferSchema=True)

ratings.rdd.getNumPartitions()     # 1 (one 2.4 MB file)

r4 = ratings.repartition(4)        # shuffle into 4 parts
r4.rdd.getNumPartitions()          # 4
r4.rdd.glom().map(len).collect()
# [25209, 25209, 25209, 25209]  rows per partition

r4.coalesce(1).rdd.getNumPartitions()  # 1 (merge, no shuffle)

spark.conf.get("spark.sql.shuffle.partitions") # '200'
  • Too few partitions → idle cores, huge tasks, out-of-memory errors.
  • Too many → thousands of tiny tasks; scheduling overhead wins.
  • Rule of thumb: 2–4 partitions per core, roughly 100–200 MB each. Files are split at 128 MB by default.
  • After a shuffle Spark uses 200 partitions, but Adaptive Query Execution (on by default since 3.2) merges the small ones for you.

Two types of operations

Transformations lazy

Take a dataset and return a new dataset. Nothing is computed yet: Spark adds a step to the plan. This is the T in ETL: where your business logic lives.

selectfilter / wherewithColumngroupByjoinorderBymapflatMap
Actions eager

Ask for a result. Spark optimises the whole plan, splits it into jobs → stages → tasks and runs them on the executors.

showcountcollecttakefirstforeachreducewrite…

Three facts about transformations: ① data structures are immutable · ② transformations are lazily evaluated · ③ they are triggered by actions.

2.2 Transformations: data is immutable

good = ratings.filter(F.col("rating") >= 4.0)

ratings.count()   # 100836  ← the original is untouched
good.count()      # 48580

Every transformation on an RDD or DataFrame returns a new one. You never "update" data in place: you assign the result to a variable.

Common mistake: ratings.filter(...) on its own line does nothing useful. Write good = ratings.filter(...).

Transformations are lazily evaluated

Spark doesn't compute a transformation right away. It keeps track of the chain of transformations and only runs it when an action asks for a result.

good = ratings.filter(...)
0.03 s
good.count()
0.50 s
transformation: just a planaction: real work

Measured on the MovieLens ratings, local mode, 4 cores.

Think of a restaurant order. The waiter writes down starter, main and dessert (transformations). The kitchen only starts cooking when you say "that's all" (the action).

Because Spark sees the whole order first, it can optimise it: drop unused columns, filter early, skip work nobody asked for.

Narrow vs wide transformations

See it yourself with explain()

Narrow: filter + select

2.3 Actions

Transformations only build up the logical plan. The real work happens when an action is triggered. Three kinds of actions:

🖥View data in the console

show(5) prints the first rows as a table. Your everyday debugging tool.

📥Collect to the driver

count(), first(), take(n), collect(), reduce() return Python values or lists of rows to your program.

💾Write to storage

df.write.parquet(…), .saveAsTable(…), rdd.saveAsTextFile(…) save the result to HDFS, S3, MinIO, tables…

Each action launches a job. Watch them appear in the Spark UI at localhost:24040 → Jobs. Two actions on the same DataFrame = the plan runs twice (unless you cache it).

The same pipeline in PySpark

from pyspark.sql import functions as F

base    = "hdfs://localhost:9000/datalake/raw/movielens"
opts    = dict(header=True, inferSchema=True)
ratings = spark.read.csv(f"{base}/ratings", **opts)
movies  = spark.read.csv(f"{base}/movies", **opts)

top = (ratings
       .groupBy("movieId")              # transformation
       .agg(F.count("*").alias("n"),
            F.round(F.avg("rating"), 2).alias("avg"))
       .filter("n >= 50")               # popular only
       .join(movies, "movieId")         # add the title
       .orderBy(F.desc("avg"), F.desc("n"))
       .select("title", "n", "avg"))
# …still nothing has run
top.show(5, truncate=False)            # ← ACTION

Good news: Spark already does some of this for you

We wrote the filter after the join, and never said which columns to read:

q = (ratings.join(movies, "movieId")
            .filter(F.col("rating") == 5.0)
            .select("title"))
q.explain(mode="formatted")

Spark's Catalyst optimizer rewrote the plan:

  • Predicate pushdown: filter before the join
  • Column pruning: userId, timestamp and genres are never read
  • Broadcast join: movies is small, so it's copied to every executor: no shuffle
What Spark actually runs (trimmed) 
Project [title]
+- BroadcastHashJoin [movieId]
   :- Project [movieId]
   :  +- Filter (rating = 5.0)       ← moved down
   :     +- Scan csv ratings
   :          ReadSchema: movieId, rating
   +- BroadcastExchange
      +- Scan csv movies
           ReadSchema: movieId, title

This only works with DataFrames and SQL. With RDDs, Spark can't look inside your Python functions, so you are the optimizer.

Caching: reuse instead of recompute

joined = ratings.join(movies, "movieId").cache()  # lazy too!

joined.count()        # 100836 ← 1st action: compute + store
joined.is_cached      # True
joined.storageLevel   # Disk Memory Deserialized 1x Replicated

# 2nd, 3rd… actions read from memory, not from HDFS
joined.groupBy("genres").count().show(3)
joined.filter("rating = 5").count()

joined.unpersist()    # free the memory when you're done
  • cache() is a transformation: nothing is stored until the first action.
  • For DataFrames it means MEMORY_AND_DISK: partitions that don't fit spill to local disk.
  • Use persist(StorageLevel…) to choose another level.
  • See cached data in the Spark UI → Storage tab.
Don't cache everything. Memory is shared with execution: caching a DataFrame you use once only slows Spark down.

Low-level API

RDDs and distributed shared variables

Low-level APIs: when do you need them?

The Structured APIs are built on the low-level APIs, so these are Spark's fundamental primitives. You won't normally use them, unless:

  • You need functionality not available in the high-level APIs (very custom partitioning, raw unstructured records…).
  • You maintain legacy code written with RDDs.
  • You want to understand what Spark does under the hood (today's goal 🎯).
Structured APIsDatasetsDataFramesSQL
Low-level APIs · SparkContextRDDsDistributed variables
⚠ 2026 reality check: the RDD API and SparkContext are not available on Spark Connect, and so not on Databricks serverless or Free Edition. They work in OSBDET (classic Spark).

RDD: Resilient Distributed Dataset

The only data abstraction in Spark 1.x: an immutable, partitioned collection of records that can be operated on in parallel.

  • Resilient: Spark remembers the lineage (the steps that built each partition) and recomputes a lost one.
  • Distributed: partitions live on many executors.
  • Dataset: each record is a plain Python object of your choice (string, tuple, dict…). No rows, no columns, no schema.

Records are raw Python objects

sc = spark.sparkContext                # entry point
lines = sc.textFile(
    "hdfs://localhost:9000/datalake/raw/movielens/movies")

lines.take(3)
# ['movieId,title,genres',
#  '1,Toy Story (1995),Adventure|Animation|…',
#  '2,Jumanji (1995),Adventure|Children|Fantasy']

header = lines.first()
rows   = lines.filter(lambda l: l != header)
rows.count()                          # 9742

# naive parsing: split each line on commas
bad = rows.map(lambda l: l.split(",")) \
          .filter(lambda r: len(r) != 3)
bad.count()                           # 2079 😱

With RDDs, you parse every record. Each one is just a string:

textFile → record'11,"American President, The (1995)",Comedy|…'

2,079 of 9,742 titles contain commas. The DataFrame CSV reader understands quotes and gives you typed columns for free. That's why DataFrames won.

RDDs in action: movies per genre

genres = (rows
  .map(lambda l: l.rsplit(",", 1)[1].strip())  # last field
  .flatMap(lambda g: g.split("|")))            # 1 → N

top5 = (genres
  .map(lambda g: (g, 1))                          # (key, value)
  .reduceByKey(lambda a, b: a + b)               # shuffle!
  .sortBy(lambda kv: -kv[1])
  .take(5))                                         # ACTION

print(top5)
print(genres.distinct().count())

Distributed shared variables

Shared variables in code

Accumulator: a global counter 
no_genres = sc.accumulator(0)

def check(line):
    if line.strip().endswith("(no genres listed)"):
        no_genres.add(1)

rows.foreach(check)        # action, runs on executors
print(no_genres.value)     # 34

Typical use: count records that don't follow a condition (bad lines, nulls…) while processing.

Broadcast: a lookup table on every node 
# {movieId: title}, built from the movies RDD (small!)
titles = dict(rows.map(parse_title).collect())
bt = sc.broadcast(titles)

ratings_rdd.map(lambda x: (bt.value[int(x[1])],
                           float(x[2]))).take(3)
# [('Toy Story (1995)', 4.0),
#  ('Grumpier Old Men (1995)', 4.0),
#  ('Heat (1995)', 4.0)]

With DataFrames you rarely need this: Spark broadcasts small tables in joins automatically (under 10 MB by default), or use F.broadcast(movies).

DataFrames

The most common Structured API: a table of data with rows and columns, potentially spanning thousands of computers.

Schema: the list of columns and their data types.

Same idea as DataFrames in pandas or R, but those live on one machine.

Schemas: let Spark guess, or tell it

from pyspark.sql.types import (StructType, StructField,
                               IntegerType, DoubleType, LongType)

# Option 1 · explicit StructType
schema = StructType([
    StructField("userId",    IntegerType()),
    StructField("movieId",   IntegerType()),
    StructField("rating",    DoubleType()),
    StructField("timestamp", LongType())])

# Option 2 · the same schema as a DDL string
schema = "userId INT, movieId INT, rating DOUBLE, timestamp LONG"

ratings = spark.read.csv(path, header=True, schema=schema)
ratings.printSchema()

DataFrames vs Datasets

Inside the Structured APIs we have DataFrames and Datasets. The difference is when Spark checks types:

  • DataFrames: at runtime. A type mismatch only shows up when the code runs.
  • Datasets: at compile time. The compiler warns you before you run anything.
Datasets exist only in Scala and Java, which have a compiler and static types. So there are no Datasets in PySpark and we won't use them. In Scala, a DataFrame is just a Dataset[Row].
Scala, for reference only 
case class Rating(userId: Int, movieId: Int,
                  rating: Double, timestamp: Long)

val ds = spark.read.option("header", "true")
  .schema("userId INT, movieId INT, rating DOUBLE, " +
          "timestamp LONG")
  .csv(path).as[Rating]

ds.filter(r => r.rating >= 4.0)     // ✓ compiles
ds.filter(r => r.rating == "high") // ✗ compile error:
                                    //   Double vs String

So, when does PySpark tell you something is wrong?

Wrong column name caught right away
ratings.select("ratin")   # typo, no action yet
AnalysisException: [UNRESOLVED_COLUMN.WITH_SUGGESTION]
A column or function parameter with name `ratin`
cannot be resolved. Did you mean one of the
following? [`rating`, `movieId`, …]

Spark analyses the plan as you build it, so names are checked immediately. (On Spark Connect this waits until the action.)

Bad data in a column only at the action
bad = spark.createDataFrame([("4.5",), ("five",)], ["r"])
x = bad.select(F.col("r").cast("double"))  # fine…
x.show()                                   # 💥 now
[CAST_INVALID_INPUT] The value 'five' of the type
"STRING" cannot be cast to "DOUBLE" because it is
malformed. … Use `try_cast` to tolerate malformed
input and return NULL instead.

Spark 4 runs in ANSI mode by default: bad casts fail. Spark 3.5 silently returns NULL.

Spark SQL from Python: spark.sql()

# 1. register DataFrames as temporary views
ratings.createOrReplaceTempView("ratings")
movies.createOrReplaceTempView("movies")

# 2. query them: the result is a DataFrame
best = spark.sql("""
    SELECT m.title, COUNT(*) AS n,
           ROUND(AVG(r.rating), 2) AS avg
    FROM ratings r
    JOIN movies m ON r.movieId = m.movieId
    GROUP BY m.title
    HAVING COUNT(*) >= 50
    ORDER BY avg DESC, n DESC
    LIMIT 5
""")
best.show(truncate=False)

# 3. mix: keep going with the DataFrame API
best.filter(F.col("n") > 100).count()   # 3

Spark SQL, Hive and catalogs

  • Since Spark 2.0 the SQL parser supports ANSI SQL and HiveQL.
  • Spark SQL can connect to the Hive metastore, where Hive keeps table metadata (schema, location, partitions), and read the data underneath.
  • Moving Hive workloads to Spark is a classic way to modernise a legacy Hadoop platform.
  • Today the same role is also played by lakehouse catalogs: Unity Catalog, AWS Glue, Iceberg REST catalogs.

RDDs vs DataFrames

Why the high-level API wins, and what's new in Spark 4

Why DataFrames are faster from Python

Catalyst can't look inside a Python lambda, and every row has to cross between the JVM and Python. With DataFrames, PySpark is as fast as Scala.

Same question, two APIs

RDD low-level
lines = sc.textFile(".../ratings")
recs  = (lines.filter(lambda l: not l.startswith("userId"))
              .map(lambda l: l.split(",")))
(recs.map(lambda x: (int(x[1]), (float(x[2]), 1)))
     .reduceByKey(lambda a, b: (a[0]+b[0], a[1]+b[1]))
     .filter(lambda kv: kv[1][1] >= 50)
     .mapValues(lambda s: round(s[0] / s[1], 2))
     .sortBy(lambda kv: -kv[1])
     .take(3))
[(318, 4.43), (858, 4.29), (750, 4.27)]

Record = string → list of strings → tuples you manage by hand. No titles, no names.

DataFrame high-level
ratings = spark.read.csv(".../ratings",
                         header=True, inferSchema=True)
(ratings.groupBy("movieId")
        .agg(F.count("*").alias("n"),
             F.round(F.avg("rating"), 2).alias("avg"))
        .filter("n >= 50")
        .orderBy(F.desc("avg"))
        .take(3))
[Row(movieId=318, n=317, avg=4.43),
 Row(movieId=858, n=192, avg=4.29),
 Row(movieId=1276, n=57, avg=4.27)]

Just Rows with named, typed columns, and Catalyst optimises it. (Several movies tie at 4.27.)

Summary

What to remember

Spark has two APIs

Low-level API
Data abstraction
Distributed collection: RDD
Also
Broadcast variables, accumulators
Entry point
SparkContext
Records
Raw Python objects, no schema
Use for
Legacy code and special cases
High-level (Structured) API
Data abstraction
Distributed tables: DataFrames, SQL, Datasets (Scala and Java only)
Entry point
SparkSession
Records
Rows with a schema of Spark data types
Under the hood
Catalyst plan → relies on the low-level API
Use for
Almost everything

Both APIs share the same operations

Transformations lazy

Create a new "virtual" version of the data; the original is immutable.

Narrow (1 → 1, no movement) or wide (shuffle, new stage).

Actions eager

Fire the computation of all the transformations applied so far, and show, return or write the result.

Each action = one or more jobs in the Spark UI.

  • Partitions drive parallelism: one task per partition, one task per core at a time.
  • Filter and select early, shuffle little, cache only what you reuse, avoid collect() on big data.

Try it yourself on MovieLens

① RDD

Which rating value is the most common? Use textFile, map to (rating, 1), reduceByKey and sortBy.

② DataFrame

Which genre has the best average rating? join ratings and movies, explode(split(genres, "\\|")), then groupBy + agg.

③ Spark SQL

How many movies have never been rated? Try LEFT ANTI JOIN or NOT EXISTS with spark.sql().
