Try it yourself: three useful endpoints

From a terminal (curl + jq)

# how many bike points?
curl -s https://api.tfl.gov.uk/BikePoint | jq 'length'
# name and bikes available at the first 3 stations
curl -s https://api.tfl.gov.uk/BikePoint | jq '.[:3][] | {name: .commonName,
   bikes: (.additionalProperties[] | select(.key=="NbBikes") | .value)}'

Try it yourself: Python in OSBDET's Jupyter

import requests

r = requests.get("https://api.tfl.gov.uk/BikePoint", timeout=30)
stations = r.json()
print(len(stations), "bike points")

def prop(station, key):
    for p in station["additionalProperties"]:
        if p["key"] == key:
            return int(p["value"])

top = sorted(stations, key=lambda s: prop(s, "NbBikes"),
             reverse=True)[:5]
for s in top:
    print(prop(s, "NbBikes"), s["commonName"])
Output (one run in October 2026; yours will differ)799 bike points51 Royal College Street, Camden Town50 Waterloo Station 2, Waterloo46 Doric Way , Somers Town…
Why bother? Exploring the data first tells you its size (about 2 MB per call), its shape and how often it changes. The API caches responses for about a minute, so polling every 5 minutes is plenty.

NiFi 2 exports flows as JSON flow definitions (the old XML templates are gone). Keep them in Git!

What's inside a flow definition?

// simplified excerpt of TfL_Data_Ingestion.json
{
  "flowContents": {
    "name": "TfL Data Ingestion",
    "processors": [{
      "name": "TfL Bike Point Data",
      "type": "org.apache.nifi.processors.standard.InvokeHTTP",
      "schedulingStrategy": "TIMER_DRIVEN",
      "schedulingPeriod": "5 min",
      "properties": {
        "HTTP Method": "GET",
        "HTTP URL": "https://api.tfl.gov.uk/BikePoint"
      },
      "autoTerminatedRelationships":
        ["Failure", "No Retry", "Original", "Response", "Retry"]
    }],
    "connections": []
  }
}

Everything you configured in the UI is in the file:

  • The Process Group and its name
  • Each processor: type, schedule and properties
  • Which relationships are auto-terminated
  • The connections between processors (none yet)
Flows as code: because it's plain JSON, you can version, review and share flows like any other code.

A · Split the list

Connect Response to SplitJson with JsonPath $.*. How many FlowFiles come out?

B · Extract fields

Use EvaluateJsonPath to put $.commonName and $.lat in attributes. Check them in provenance.

C · Land the data

Write each station with PutFile (e.g. /tmp/tfl) or to MinIO with PutS3Object.

Remember to un-terminate the Response relationship once it has somewhere to go.
