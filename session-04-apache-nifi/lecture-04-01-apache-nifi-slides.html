What is NiFi?

Enterprise data flow at scale

What is it?

Apache NiFi is an easy-to-use, powerful and reliable system to ingest and distribute data, addressing the challenges of enterprise data flow at scale.

NiagaraFiles

NiagaraFiles, the original project name

NSA → Apache

Created at the US National Security Agency, donated to Apache in 2014

NiFi 2

Current major version (2.12, September 2026)

Three pillars

Easy to use

Flows are designed, configured, controlled and monitored from a web UI: drag components onto a canvas and connect them.

Powerful

Highly configurable, scales to demanding throughputs (>100,000 events/sec), built-in security and data provenance, extensible in Java or Python.

Reliable

Guaranteed delivery when needed, plus failover and recovery mechanisms.

FlowFile

A FlowFile is a unit of data moving through the system: a small record or an entire file.

It has two parts:

  • Attributes: key–value metadata
  • Content: the payload, as bytes
Attributesuuid = 9f3c…filename = update-1042.jsonpath = ./mime.type = application/json
Contentbyte[] {"message": {"text": "…"}}

Content vs attributes

Example: a Telegram message ingested into NiFi becomes a FlowFile. The message JSON is the content; its ID or chat type can be stored as attributes.

Content

  • Stores the data itself and rarely changes
  • Transforming the original data is not good practice
  • Enrich instead: add information without modifying the original

Attributes

  • Can be added, altered or removed
  • Used for routing and extra information
  • Every FlowFile has uuid, filename and path

Processor

Processors perform the work: extraction, filtering, transformation and loading, with access to both attributes and content. NiFi ships with almost 300.

InvokeHTTP calls the Telegram Bot API and creates a FlowFile per response. Each relationship (Response, Failure, Retry…) goes to its own connection.

Connection

Connections route FlowFiles between processors, one per relationship.

They act as queues, so processors can work at different rates (buffering).

Back pressure: when a queue fills up, NiFi pauses the upstream processor. Default: 10,000 FlowFiles or 1 GB.

NiFi architecture

Standalone and multi-node cluster

Standalone: everything on one server

Local storage
  • Web server: the UI and REST API
  • Flow Controller: runs processors and extensions
  • FlowFile repository: the state of every FlowFile
  • Content repository: the actual bytes
  • Provenance repository: the history of each FlowFile

State lives on disk, so NiFi recovers after a crash.

Multi-node cluster: many servers together

  • Every node runs the same flow on a different share of the data
  • A client can talk to any node; changes are replicated to all
Cluster coordinator: manages membership
Primary node: runs tasks that must happen only once
Coordination client: every node

NiFi 2 can coordinate with ZooKeeper or with Kubernetes.

Summary

And what's new in NiFi 2

Summary

  • NiFi is an easy-to-use, powerful and reliable system for enterprise data ingestion at scale.
  • It protects ingestion with buffering and back pressure when data arrives faster than it can be written.
  • It provides guaranteed delivery and data provenance.
  • It scales horizontally by adding nodes or clusters.

What's new in NiFi 2

  • New web UI
  • Python processors
  • Java 21 required
  • JSON flow definitions and Git-based registry clients replace XML templates
  • Kubernetes-native clustering

  • Airflow 3 runs workflows written in Python as DAGs (graphs of tasks)
  • Triggers: schedules, sensors (FileSensor, S3KeySensor, HttpSensor) or updated assets
  • Raw files land unchanged in storage: enrich, don't transform, as with NiFi
  • Pass small values (file paths) between tasks, not whole datasets

Example DAG: Telegram updates to MinIO

from airflow.sdk import dag, task, Variable
from airflow.providers.http.sensors.http import HttpSensor
from airflow.providers.amazon.aws.hooks.s3 import S3Hook
@dag(schedule="@hourly", start_date=datetime(2026, 10, 1), catchup=False)
def telegram_to_minio():
    api_ready = HttpSensor(task_id="api_ready", http_conn_id="telegram_api", endpoint="",
                           poke_interval=60, timeout=600, mode="reschedule")   # sensor
    @task
    def extract() -> list:
        token = Variable.get("telegram_token")
        r = requests.get(f"https://api.telegram.org/bot{token}/getUpdates", timeout=30)
        r.raise_for_status()
        return r.json()["result"]
    @task
    def load(updates: list, ts_nodash=None) -> str:
        key = f"raw/telegram/{ts_nodash}.json"                              # one file per run
        S3Hook(aws_conn_id="minio").load_string(json.dumps(updates), key=key,
                                              bucket_name="datalake", replace=True)
        return key
    api_ready >> load(extract())

NiFi or Airflow?

Apache NiFiPython + Airflow
How you buildVisual canvasPython code, versioned in Git
Data handlingContinuous flow of FlowFilesBatches, run by run
TriggersAlways running; processors poll or listenSchedules, sensors, assets
Built-in safetyBack pressure, provenance, guaranteed deliveryRetries, backfills, run history
Sweet spotMany sources, near real-time routingScheduled batch ingestion with custom logic
They are often combined: NiFi or Kafka moves data continuously, and Airflow orchestrates the batch jobs that come after.
