Two types of storage

The goal of this layer is to store all the data at scale.

Batch storage · volume

  • Almost every big data architecture needs a file-based store to keep all the data in bulk
  • Long-term: data stays for years
  • HDFS, MinIO, Amazon S3, ADLS, Cloud Storage

Streaming storage · velocity

  • A specialised store for streaming and real-time data
  • Simplifies real-time processing
  • Usually transient: data is kept for hours or days
  • Kafka, Pulsar, Event Hubs, Pub/Sub

Worker nodes: storage + compute together

Hadoop runs the processing on the nodes where the data is stored.

Move the code to the data, not the data to the code.

The reason: in 2008, moving data through the network was the bottleneck.

The catch: the cluster can never sleep

zzzzzzzzzzzzzzzzzz
$ $ $24 × 7 × 365

Storage and compute live on the same machines, so every node must stay up, even when no job is running, just to read and write files.

In the cloud, that hurts: you pay per use. Few companies can afford hundreds of nodes running 24×7×365 just to keep data available.

Storage and compute apart

Clouds offer separate services for storage and processing. Networks are no longer the bottleneck, and storing large amounts of data is cheap.

Ephemeral clusters

object
storage
1 · Create cluster2 · Read data3 · Compute4 · Write results5 · Destroy cluster

The trend in the cloud is to process data on ephemeral clusters:

  • Reserve a cluster with the processing power you need
  • Process the data and store the results
  • Switch the cluster off

Today many services go further: serverless engines (BigQuery, Databricks serverless, AWS Glue) start and stop compute for you.

2.1 Open source: Hadoop HDFS

The Hadoop Distributed File System is a distributed, scalable and portable file system that can store any type of data.

  • Created at Yahoo!, inspired by Google's GFS paper
  • Files are split into blocks (128 MB by default)
  • Each block is replicated 3 times on different nodes
  • The NameNode keeps the metadata: which blocks make up each file and where they live
trips.csv · 300 MB
A · 128 MBB · 128 MBC · 44 MB
NameNodeA → 1,2,3 · B → 2,3,4 · C → 1,3,4
DataNode 1AC
DataNode 2AB
DataNode 3ABC
DataNode 4BC

Lose a node? Every block still has two copies.

2.1 Open source: MinIO

MinIO is a high-performance object storage server, API-compatible with Amazon S3.

  • Stores unstructured data: photos, videos, logs, backups, container images, data lake files
  • Any S3 tool or library works with it (boto3, Spark's s3a://, the AWS CLI)
  • Included in OSBDET: your local S3

2025–2026 update

  • May 2025: the admin console was removed from the free community edition
  • Oct 2025: free binaries and Docker images stopped
  • Dec 2025: the community repository entered maintenance mode, and was later archived

OSBDET ships an earlier release, fine for learning. Open-source S3 alternatives: Ceph RGW, SeaweedFS, Garage.

2.2 Cloud object storage

Amazon S3AWS

Simple Storage Service: the reference object store, with industry-leading scalability, availability and durability.

Now also S3 Tables: managed Apache Iceberg tables
Azure Data Lake StorageAzure

Blob storage with a hierarchical namespace: real folders, fine-grained permissions, built for analytics. Trillions of files; single files over a petabyte.

Gen1 was retired in 2024; use Gen2
Google Cloud StorageGoogle Cloud

Object storage for any type of data on Google Cloud, used directly by BigQuery, Dataproc and Vertex AI.

Buckets can be regional, dual-region or multi-region
Not a file system? Object stores are often called "file-based" because you store files in them, but under the hood they're buckets of objects reached over HTTP.

Why a separate streaming store?

Hadoop was designed with only two Vs in mind: volume and variety.

As data gained speed (velocity), we needed to react, analyse and process it while it's still in motion.

Examples: fraud alerts, live bike availability, sensor alarms, recommendations as you browse.

3.1 Open source: Apache Pulsar

Apache Pulsar is a distributed pub-sub messaging platform, similar to Kafka. Created at Yahoo!

  • Separates serving (brokers) from storage (Apache BookKeeper)
  • Built-in multi-tenancy and geo-replication
  • Adoption has been much smaller than Kafka's

Summary

The storage layer by provider

Summary

  • Almost every big data solution needs both a batch store and a streaming store.
  • The options depend on where you deploy: on premises or in the cloud.
  • The cloud separates storage from compute: cheap, always-on object storage plus on-demand processing.
  • The storage layer holds all the data (the data lake), so design it carefully for security, data quality and governance.

Hands-on in OSBDET

Touch each storage technology yourself

HDFS from the command line

Turn Hadoop on in the WebUI, open a terminal in OSBDET's Jupyter and try:

# create a folder and upload a file
hdfs dfs -mkdir -p /data/raw/tfl
curl -s https://api.tfl.gov.uk/BikePoint -o bikepoint.json
hdfs dfs -put bikepoint.json /data/raw/tfl/

# list it and see how HDFS stored it (blocks and replicas)
hdfs dfs -ls -h /data/raw/tfl
hdfs fsck /data/raw/tfl/bikepoint.json -files -blocks
Browse the same files in the HDFS UI at localhost:50070 → Utilities → Browse the file system. OSBDET runs a single node, so you'll see 1 replica instead of 3.

MinIO with Python (the S3 API)

import boto3, requests

s3 = boto3.client(
    "s3",
    endpoint_url="http://localhost:9000",  # MinIO inside OSBDET
    aws_access_key_id="osbdet",
    aws_secret_access_key="osbdet123$",
)

s3.create_bucket(Bucket="datalake")

data = requests.get("https://api.tfl.gov.uk/BikePoint").content
s3.put_object(Bucket="datalake",
              Key="raw/tfl/bikepoint.json", Body=data)

for obj in s3.list_objects_v2(Bucket="datalake")["Contents"]:
    print(obj["Key"], obj["Size"])

The same code works with Amazon S3: remove endpoint_url and use your AWS credentials.

Check the result in the MinIO console at localhost:29001 (user osbdet, password osbdet123$).

Kafka from the command line

Turn Kafka on and open two terminals: one producer, one consumer.

# 1. create a topic with 3 partitions
kafka-topics.sh --bootstrap-server localhost:9092 --create --topic bike-status --partitions 3
# (the .sh scripts live in Kafka's bin/ folder)

# 2. terminal A: type one event per line
kafka-console-producer.sh --bootstrap-server localhost:9092 --topic bike-status
> {"id": "BikePoints_1", "NbBikes": 7}

# 3. terminal B: read everything from the beginning
kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic bike-status --from-beginning
Try this: stop the consumer, send more events, start it again with --from-beginning. The old events are still there: Kafka stores them, it doesn't just pass them on.
