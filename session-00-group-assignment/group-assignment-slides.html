Define your use case

Relevant beats complicated

What makes a use case relevant

"As a [stakeholder], we want to know [question] so that we can [decision]."

Example: As the Santander Cycles operations team, we want to know which stations run empty or full, and when, so that we can plan van rebalancing routes.
Example: As a retail trader, we want to know at which hours BTC/USDT is most volatile and liquid so that we can time our orders.
  1. A real stakeholder who would act on your answer.
  2. 3 to 5 business questions, measurable with your data (a number, a ranking, a trend).
  3. Feasible: the API gives that data, and you can collect enough of it (start early: data accumulates over time).
  4. Big data justified: many snapshots, many entities, several sources.
  5. Honest: say what your data can't answer.
Avoid: "we analysed the data" with no question, or questions answered by a single API call.

Build the pipeline

Ingestion → storage → processing, step by step

3.1 Ingestion with NiFi: requirements

Minimum
  1. One NiFi flow (Process Group) per source, scheduled: every minute, every 5 minutes… whatever your questions need.
  2. Collect continuously for long enough to answer your questions: start in the first phase of the project.
  3. File names with the collection time, e.g. bikepoint_yyyyMMdd_HHmm.json.
  4. Files written to HDFS with PutHDFS, into the raw layer.
  5. Flows exported as flow definitions (JSON), without credentials.
Going further
  • JSON arrays → JSON Lines (Split + Merge), as in lab 16.1.
  • Error handling: retry, and route failure somewhere visible.
  • A historical backfill (Binance dumps, TfL journey CSVs) loaded with ListFile → FetchFile → PutHDFS (lab 8.1).
  • A streaming path to Kafka next to the batch path (lab 8.2).
  • An enrichment source (weather, calendar, sentiment) with its own flow.
Remember lab 5.1: sensitive values (keys, passwords) are not exported with a flow. Document which ones must be filled in after an import.

3.2 Storage in an HDFS data lake

/datalake
├── raw/                       # as ingested, never edited
│   ├── tfl/bikepoint/yyyy/MM/dd/
│   │   └── bikepoint_yyyyMMdd_HHmm.json
│   └── openmeteo/weather/…/
├── curated/                   # clean, typed, Parquet
│   ├── tfl/bikepoint_status/
│   │   └── dt=…/part-0000.parquet
│   └── openmeteo/weather_hourly/
└── analytics/                 # answers to your questions
    ├── station_empty_hours/
    └── demand_vs_rain/

Pattern from the course: /<layer>/<source>/<dataset>/…

Minimum
  • The three layers, with one folder per source and dataset.
  • Raw stays in its original format; curated is Parquet, partitioned by date.
  • Show it: hdfs dfs -ls -R /datalake and hdfs dfs -du -h /datalake in your slides.
Going further
  • Fix the small files problem: thousands of tiny JSON files → a few Parquet files per day.
  • Compare sizes raw vs curated (lecture 6.2: Parquet was 24× smaller than CSV).
  • Delta Lake tables in curated, or MinIO as a second store.
Never edit raw data. If your cleaning has a bug, you can always rebuild curated from raw.

3.3 Notebook ①: data engineering (raw → curated)

raw = spark.read.json("hdfs://localhost:9000/datalake/raw/tfl/bikepoint/*/*/*/*.json")\
           .withColumn("file", F.col("_metadata.file_path"))

status = (raw
  .withColumn("p", F.explode("additionalProperties"))  # ① flatten
  .groupBy("file", "id", "commonName", "lat", "lon")
  .pivot("p.key", ["NbBikes", "NbEBikes", "NbEmptyDocks", "NbDocks"])
  .agg(F.first(F.col("p.value").cast("int")))  # ② wide, typed
  .withColumn("ts", F.to_timestamp(  # ③ snapshot time
      F.regexp_extract("file", r"(\d{8}_\d{4})", 1), "yyyyMMdd_HHmm"))
  .withColumn("dt", F.to_date("ts"))
  .dropDuplicates(["id", "ts"]))  # ④ dedupe

(status.repartition("dt").write.mode("overwrite")  # ⑤ Parquet
       .partitionBy("dt").parquet("hdfs://localhost:9000/datalake/curated/tfl/bikepoint_status"))
  1. Flatten nested JSON with explode (labs 16.1, 18.1).
  2. Long → wide and cast: numbers as numbers, never as text.
  3. Time from the file name, not from modified.
  4. Deduplicate: APIs repeat unchanged records.
  5. Write Parquet, partitioned by date.
Prove data quality: rows in vs rows out, nulls per column, min/max per numeric column, number of snapshots per day. Put the table in your slides.

Binance version: klines arrive as arrays → F.col("value")[i] by position, prices cast to double, timestamp_millis(openTime).

3.4 Notebook ②: data analytics (curated → insights)

Follow the EDA of lab 17.1
  1. Metadata: schema, size, samples, entities, metrics, dimensions.
  2. Profiling: summary(), nulls, distinct values, most and least frequent.
  3. Business questions, one section each, with the DataFrame API and Spark SQL (temporary views, lab 18.1).
  4. Enrichment joins (weather, calendar, sentiment).
  5. Save the answers to analytics/.
status = spark.read.parquet("hdfs://localhost:9000/datalake/curated/tfl/bikepoint_status")
status.createOrReplaceTempView("status")

empty_by_hour = spark.sql("""
  SELECT id, commonName, HOUR(ts) AS hour,
         ROUND(AVG(CASE WHEN NbBikes = 0 THEN 1 ELSE 0 END) * 100, 1)
           AS pct_time_empty,
         COUNT(*) AS snapshots
  FROM status
  GROUP BY id, commonName, HOUR(ts)
  HAVING COUNT(*) >= 20""")

# window functions: change since the previous snapshot
from pyspark.sql import Window
w = Window.partitionBy("id").orderBy("ts")
moves = status.withColumn("delta", F.col("NbBikes") - F.lag("NbBikes").over(w))

# plot only small, aggregated results
pdf = empty_by_hour.groupBy("hour").agg(F.avg("pct_time_empty")).toPandas()

Results, presentation and deliverables

Insights, a clear story and a complete package

What counts as an insight

💡 Number + context + "so what"

"Between 8 and 9 am, 12 stations around Waterloo are empty over 40% of the time (in our data), so a rebalancing van there before 8 am would serve the morning peak."

Illustrative example, not a real result.

Not an insight: "BTC price went up and down", "there are 797 bike points", a raw table screenshot.
  • One chart per question, with a title that states the finding.
  • Say "% of what" and the size of every group; set minimum volumes.
  • Compare: hours, days, stations, pairs, rain vs dry.
  • State your collection period and its limits (a week ≠ a year).
  • End with recommendations and what you'd do with more time or data.
Remember lab 17.1: sanity-check every number before it goes on a slide.

Frequently asked questions

Can we store in MinIO instead of HDFS?HDFS is required. MinIO can be an additional store (extra credit).
Can we download files by hand and upload them?No: ingestion must go through NiFi. A historical backfill can be loaded with NiFi from a local folder (lab 8.1).
How much data is enough?Enough to answer your questions with confidence: several days of snapshots is a good target for time patterns. Say what you have.
Both scenarios at once?Yes, if the use case links them. One well-done scenario beats two shallow ones.
Can we use pandas?Yes, on small aggregated Spark results for charts. Processing must be in Spark.
Spark 3.5 (OSBDET) or Spark 4?OSBDET's Spark is fine. Mind the differences seen in class (ANSI mode in Spark 4).
Can we use AI assistants?Follow IE's academic integrity rules; disclose any tool you used in the references. You must be able to explain every line.
Our collection stopped for a day. Problem?No, if you detect it, document the gap and avoid conclusions that depend on it.

Questions? Good luck!
